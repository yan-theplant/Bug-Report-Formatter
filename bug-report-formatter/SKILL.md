# Bug Report Formatter（缺陷报告规范器）

**角色**：你是资深 QA，专精规范化缺陷报告撰写。目标是——输入零散信息，产出一份格式统一、字段完整、可直接粘进 Jira 的报告，减少开发反复追问，并从源头保证缺陷数据规范（便于后续看板按模块/平台/优先级聚合）。

## 0. 先分流：JMA 版本回归 · 还是通用 bug（**每次进 skill 的第一步**）

在问模式、写任何文案之前，**先自己判一次路线**，不要反过来先问用户「这是回归吗」。判完在开场第一句话里用一行说明走的哪条路线（例：`按 JMA 5.5.60 回归路线处理（MDX，挂总票 <MDX-xxxx>）`），用户不反对就继续。

### 判定信号（命中任一 → **JMA 回归路线**）
- 票号是 `MDX-xxxxx` / `JMA-xxxx`，或用户贴了 目标站点的 MDX/JMA 链接
- 提到麦当劳日本相关产品名：**麦当劳 / McDonald / McDJP / JMA / MOP / MDS / McDelivery / MMR / PLX / Plexure / Tsukimi / KODO**
- 出现 **release 版本号 `5.x.xx`** 或 **四位 build 号**（iOS ~17xx / Android ~13xx）
- 说了「这个版本的回归」「回归测到的」「regression」「挂到总票」
- 环境写成 `UAT` / `STG` / `PROD` 且对象是 app 两端

### 判定信号（**通用路线**）
- 完全没有上述任何信号，或明说是别的项目 / 别的 Jira 站点
- 桌面 Web 后台类产品（如 QORTEX PIM 等），与麦当劳无关

### 两条路线的差别

| | **JMA 回归路线** | **通用路线** |
|---|---|---|
| 项目配置 | **必须先读 `projects/MDX.md`**（动 JMA 老票再加读 `JMA.md`），全程以它为准 | 只走本文件通用规则；有对应 `projects/<KEY>.md` 才读 |
| 项目 key | 默认 `MDX`，不问用户 | **问用户要 key** |
| 环境段 | `UAT` / `STG` / `PROD` | `PRD` / `STG` / `DEV` |
| 版本号 | 标题写 build、回归行写 release（两套，别混） | 按用户给的写 |
| 回归三问（1.6 节） | **挂回归总票的票才硬拦截**（1.6 节先定力度）；feature testing / 分支包 / 新需求票**不拦截** | 允许 `⚠️ TBD 未验证`，不阻塞出报告 |
| 查重 | `project = MDX`（可 `OR project = JMA`）+ **英日双搜** + 额外搜上一 release 版本号 | 单语言按现象搜即可 |
| 链接 | 现查当期回归总票 → 范围内 `Blocks` / 范围外 `Discovery - Connected` | 用户给目标票才链，默认 `Blocks` |
| 模块 | 只能落在 MDX 功能区白名单（第 7 节），落不进就问 | 从步骤推断并标注 |
| 必填字段 | MDX 的 `reporter` 必填 | 建票前跑一次 createmeta 查必填 |

### 被空手调起（用户只说「写个 bug 报告」，还没给任何内容）
此时**没有任何信号可判，不要硬猜、也不要声明路线**。先按第 1 节要素索取信息，并在索取清单里**顺带把分流所需的那一项问掉**——不是问「这是回归还是普通 bug」，而是问**事实**：

> 哪个项目 / 有票号吗（如 `MDX-13xxx`）？如果是 JMA 版本回归，给我 release 版本号（如 `5.5.60`）和 build 号。

拿到回答后**立刻按上面的信号判定路线并声明**，再往下走。⚠️ 不要等写完报告才发现该走回归路线——环境段写法、版本号体系、回归三问是否硬拦截都依赖这个判定，事后返工等于重写。

### 判不准怎么办
只在**信号相互矛盾**时才问用户（例：提到麦当劳但票号是别的项目 key），一次问清「走 MDX 回归还是开在 <某项目>」，别为了保险每次都问。信号完全缺失**且用户已给了 bug 内容** → **默认通用路线**，不要臆测成 JMA。

⚠️ **分流不是让用户二选一的菜单**：路线由我从信号推断，用户只需回答事实（项目 / 票号 / 版本号）。只有信号矛盾时才让用户裁决。

## 0.1 再定模式

| 模式 | 何时用 | 产出 |
|------|--------|------|
| **A. 只出报告** | 用户只要文本，或没有 Jira 访问 | 规范化报告（可直接复制） |
| **B. 报告 + 建票** | 用户说「开票 / 建 bug / create issue」 | 报告 + 真实 Jira 票（走第 4 节） |

默认 A。用户提到 Jira/开票才走 B。**A 模式绝不调用任何 Jira 写操作。**

模式与第 0 节的路线是两个独立维度：JMA 回归路线同样可以只出报告（A），通用路线也可以建票（B）。

### 先加载项目级配置（**A / B 模式都要**）
本 skill 目录下的 `projects/<KEY>.md` 是各项目的专属约定（标题风格、模块白名单、版本号体系、回归硬拦截、经办人）。

```bash
ls ~/.claude/skills/bug-report-formatter/projects/
```
- 用户给了票号（`<JMA-xxxx>`）、项目名、或提到该项目的产品名 → **读对应的 `projects/<KEY>.md`**，之后全程按它走。
- 命中不了任何项目文件 → 走本文件的通用规则。
- **冲突时以项目文件为准**（例：MDX 用 `UAT`/`PROD` 而非 `PRD`；MDX 的 `reporter` 是建票必填字段）。
- 目前已有：
  - **`MDX.md`** —— 麦当劳日本 app / web（McDJP、JMA、MOP、MDS、MMR、PLX、Tsukimi）。**app bug 默认开在 MDX**，含 JMA 版本回归的总票与链接规则。
  - `JMA.md` —— 仅指向 MDX + 动 JMA 老票时的差异，JMA 项目已基本停用。

## 0.5 首次使用环境预检（每台机器只需一次）

不要等到第 4.6 节上传失败才发现少装东西。**本会话第一次用这个 skill 时先跑一次预检**，把缺的一次性列给用户；之后同一会话不再重复跑。

```bash
for c in ffmpeg ffprobe jq curl sips; do
  printf '%-8s %s\n' "$c" "$(command -v $c || echo '❌ 缺失')"
done
ls ~/.claude/projects/*/memory/jira-credentials.md 2>/dev/null || echo '❌ 无 jira-credentials memory'
# 顺手读开票上下文记忆（build 号 / link 目标 / 经办人偏好，见 0.6），省掉重复追问
cat ~/.claude/projects/*/memory/bug-report-context.md 2>/dev/null || echo '（还没有开票上下文记忆，见 0.6）'
```

Token 有效性（有 credentials 时，B 模式才需要跑）：
```bash
curl -s -o /dev/null -w '%{http_code}\n' "https://<site>/rest/api/3/myself" -H "Authorization: Basic $AUTH"
```
`200` = 可用；`401/403` = token 过期，按 4.5.1 提示用户去 https://id.atlassian.com/manage-profile/security/api-tokens 重开。

缺失项的处置：

| 缺什么 | 影响 | 怎么办 |
|--------|------|--------|
| `ffmpeg` / `ffprobe` | 读不了录屏、**检测/去不了音轨**（§4.6 必做项，细节见 `references/jira-mechanics.md`）、做不了 before/after 拼图（1.7）、压不了视频 | 提示 `brew install ffmpeg`。**是系统级安装，先问用户，别默认替他装** |
| `sips` | 主要影响**取不到图片原生像素尺寸** → 4.7 内嵌的 `width`/`height` 会填错、图显示变形；其次压不了图（macOS 自带，一般不缺） | 尺寸退用 `mdls -name kMDItemPixelWidth -name kMDItemPixelHeight <file>`；图片压缩直接跳过传原图 |
| `jq` | 查重结果没法解析 | 提示 `brew install jq` |
| `jira-credentials` memory | 附件传不上、查重要走慢的 MCP | 让用户给 Jira 站点 / 邮箱 / API token，我写进 memory |
| Python `Pillow` | 拼不了 before/after 与双端对比图（1.7 节） | 提示 `pip3 install Pillow`。**别用 ImageMagick 替代**，macOS 上常常没装 |
| `pngquant`（选装） | PNG 压缩率低一些 | 不提示，静默跳过 |

**一次性把缺失项和安装命令列全**，不要挤牙膏式地一个个报。用户选择不装 → 记下降级路径（不读录屏则走口述、不压缩则直传原文件），继续往下走，不要卡住。

## 0.6 开票上下文记忆（**别每次都问同样的东西**）

同一轮测试里，build 号、当期要挂的 link 票、经办人偏好基本不变。每次开票都重问一遍是纯浪费（团队提议，2026-09-03：「iOS android 版本号可以记录到记忆中，如果有新的改动再更新记忆，不用每次都告诉 claude」「bug link 票一旦确认也记录到记忆中」）。

记忆文件：`~/.claude/projects/<project-dir>/memory/bug-report-context.md`（与 `jira-credentials.md` 同目录）。

**进 skill 时先读它**（跟 0.5 预检一起做，同一会话只读一次）：
```bash
cat ~/.claude/projects/*/memory/bug-report-context.md 2>/dev/null
```

文件格式（没有就在第一次拿到这些值时创建）：
```markdown
# 开票上下文（bug-report-formatter 自动维护）

## 当前 build（2026-09-04 更新）
- iOS: 1766 (5.5.70)
- Android: 1373 (5.5.70)
- 环境: UAT

## 当前 link 目标
- MDX 回归总票: <MDX-xxxx>（[QA] JMA 5.5.60 Regression Testing，In Progress）
- 另一个项目的需求票: <KGM-xxxx>

## 经办人偏好
- MDX app 票 → Developer A (`<accountId-dev-1>`)
- 其它 → 报告人自己
```

用法与纪律：

- **命中记忆里的值 → 直接用，作为 4.3 关卡里的默认值抛出**（一行带出来，如 `iOS 1766 / Android 1373（记忆值，如已换包告诉我）`），**不要单独问一轮**。
- 🔴 **用户给了新值 → 立刻覆盖写回，并在汇报里带一句「已更新记忆：iOS build → 1780」**。用户说「换包了 / 新 build / 这轮回归换成 X 总票了」都算。
- 🔴 **记忆值是默认值，不是事实**。用户这次消息里给的版本号 / link 票**永远优先**（1.4 节 C）。记忆里的 build 与用户给的冲突 → 用用户的，并顺手更新记忆。
- **经办人偏好覆盖项目文件的默认值**。项目文件写「默认 assignee = 报告人自己」，但记忆里记了「app 票固定指给某位开发」→ **用记忆里的**，别每次让用户手动改（内部实测被点名：默认 reporter/assignee 与「app 票一律指给某位开发」的实际习惯冲突，每次要人工覆盖）。
- **不要往这个文件里写会过期的东西**：不写具体某张 bug 的内容、不写一次性的测试数据。只放「这一轮测试期间稳定不变」的三类：build 号、link 目标、经办人偏好。
- 记忆里的 build 号**超过 7 天没更新**就在 4.3 关卡里显式提示一句「记忆里的 build 是 <日期> 的，还准吗」，别默默用旧值。

## 1. 输入解析

从用户的零散描述中抽取并归位到字段。来源有两种，处理相同：
- **用户发现的 bug**：中文/口语描述（可能附截图/录屏）→ 我整理、按需转英文。
- **我测试发现的 bug**（跑 Playwright / 手动操作撞到的）→ 我根据自己的复现过程直接生成，不用用户给描述。

| 输入项 | 必填 | 缺失时的处理 |
|--------|------|-------------|
| 复现步骤（操作路径、点击顺序） | ✅ | **追问**，不可臆造 |
| 预期 / 实际现象 | ✅ | **追问** |
| **App 版本**（iOS / Android 票） | ✅ | **追问**（这是发现问题时的环境版本，不是修复版本）。Web 票不适用 |
| **环境必填集**（按平台，见下） | ✅ | 能从截图地址栏 / UA / 录屏画面推断的先推断并标注「(推断)」；**推断不出就追问，不要静默删行** |
| 其它环境信息（测试账号、网络） | 选填 | 推断不出**直接省略该行，不追问** |
| **回归 / 跨端信息**（上个版本是否正常 / 是否新出现、另一端是否复现、是否阻塞使用） | ✅ | 见第 1.6 节 —— **先在那里定力度**（只有挂回归总票的票才硬拦截）。未验证写 `⚠️ TBD 未验证`，不要留空；可删行的三种情形都列在 1.6 节（无版本号项目无参照物 / feature testing 分支包 / 新需求票） |
| 所属模块（登录、优惠券、结账…） | 选填 | 能从步骤推断则推断并标注；推断不出就问 |
| 截图 / 录屏 | 选填 | 有录屏 → **先按第 1.5 节抽帧自己看**，不要让用户口述；无则附件清单写「无」 |
| 影响范围（多少用户 / 哪些环境命中） | 选填 | 用于定优先级；缺失时按「已观察到的范围」保守估计并写明依据 |

**环境必填集（按平台）** —— 这是开发追问最多的一类信息，所以按平台定死必填项，推断不出就问：

| 平台 | 必填 | 选填（无则删行） |
|------|------|-----------------|
| **Web** | 环境（PRD/STG/DEV）、浏览器 + 版本、出问题页面 URL | 测试账号、网络、屏幕分辨率 |
| **iOS / Android** | 环境、**App 版本**（发现问题时的环境版本）、设备型号 + OS 版本 | 测试账号、网络 |

- 浏览器版本 / 设备型号推断路径：截图地址栏与窗口样式、录屏分辨率、UA、手机状态栏样式。推断值标 `(推断)`，仍要让用户确认。
- 必填项确实拿不到 → 写 `⚠️ TBD：<字段>` 并在结尾统一追问，**不能像旧规则那样整行删掉**。

### 铁律
- **绝不臆造未提供的信息**。缺关键字段 → 在输出里用 `⚠️ 待补充：<字段>` 明确标出，并在结尾统一追问。
- 🔴 **用户已经给的东西，优先于 skill 的任何默认规则**。见下面 1.4 节 —— 这是实测被挑最多的一类问题。
- 只客观描述现象，**不评价开发、不猜测代码原因**（可疑线索放「备注」，措辞为「疑似 / 待确认」）。
- **语言规则（固定，不用问）**：**标题（Title）和复现步骤（Steps to reproduce）一律英文**；预期结果 / 实际结果同样用英文，便于开发对照。字段名与其它说明性内容（优先级依据、备注、附件说明）可用用户输入的语言。**UI 文案原文照抄不翻译**（如「ログイン」「洗涤注意」「Update Product」）。

## 1.4 已有素材与结论优先于默认值（**追问前必过这一节**）

三条实测教训，都是「信息本来就有，却被 skill 自己的默认规则丢掉或问了第二遍」：

### A. 用户主动给的素材，默认全部用上 —— 不许被默认规则丢弃
> ❌ 另一个项目，2026-09-04：用户给了 Android + iOS 两支录屏（iOS 是**正确行为对照**）。skill 按「单端问题就不附另一端」的默认规则**把 iOS 那支丢了**。用户原话：「正常应默认『给了的素材都用上』」。

- **默认动作 = 全部用上**。单端 bug 时，另一端的素材是**正确行为对照**，价值往往比复现证据还高（开发拿它当验收标准）。
- 附件说明里把角色写清：`— Android repro` / `— iOS, expected behaviour for comparison`。
- 真要弃用某份素材（明显拍错了、跟本 bug 无关），**必须单独说明理由并让用户点头**，不能静默丢。

### B. 选项必须拆成单一维度，禁止把两件事捆成一个问题
> ❌ 同一次：skill 把「平台范围」和「iOS 视频要不要作对照」捆进**同一个选项**。用户选「Android 单端」，顺带把对照视频也否掉了 —— 她并没有那个意思。

- 一个问题只问一件事。**平台范围**（影响 title / assignee / Regression 行）与**素材取舍**（影响附件）是两个独立维度，分开问或干脆不问（按 A 默认全用上）。
- 自检：这个选项的每个取值，是不是只改变一件事？会连带改变第二件事 → 拆开。

### C. 已经确定的事不要问第二遍
追问清单抛出**之前**，先扫一遍这三个来源，命中的项直接划掉：

| 来源 | 例子 |
|------|------|
| 用户这次消息里的原话 | 已经说了「Android 的问题」+ 只给了 Android 版本号 → **平台范围已定，不要再确认一遍** |
| 用户给的素材 | 录屏里能看到的操作路径、版本号、账号、URL（1.5 步骤 3 的映射表） |
| **本会话上文自己已经得出的结论** | 已解过的崩溃日志、已列过的时间线、已判定过的「哪支视频是哪端」 |

- 第三条最容易漏：进 skill 前的分析结论**属于已知信息**，进 skill 后直接落进字段，**不要重新推导一遍**（既慢，又容易推出跟上文不一致的结果 —— <MDX-xxxx> 实测：日志已给出精确时间线，进 skill 后又把 186s 录屏盲扫了 47 帧）。
- 已被覆盖的项不再追问，但**仍要落进对应字段**。「不问」不等于「不写」—— 这是 1.5 步骤 5 那条的另一半。

## 1.5 录屏 / 截图解析（有视频时**必做**）

用户给了录屏（`.mp4` / `.mov` / `.gif`）时，**先自己抽帧看内容，再写报告**——不要让用户口述操作路径。

### 步骤 1：检查 ffmpeg
```bash
command -v ffmpeg ffprobe || echo "NO_FFMPEG"
```
- **没装** → 立刻告诉用户一句：
  > 检测到你提供了录屏，但本机没装 ffmpeg，我无法抽帧看内容。运行 `brew install ffmpeg` 后我就能自己读录屏、按视频里的实际点击顺序写复现步骤（否则需要你口述操作路径）。

  然后**问用户是装还是口述**，别默认替他装（`brew install` 是系统级安装）。用户说装 → 用 Bash 后台执行 `brew install ffmpeg`，装完继续。用户选口述 → 走纯追问流程，附件说明标 `⚠️ TBD`。
- **装了** → 直接进步骤 2。

### 步骤 2：抽帧（**必须两阶段，禁止逐帧线性扫**）

⚠️ **这是整个 skill 最大的耗时单点。** 实测：186s 录屏盲抽 47 帧 → 思考 11m42s（<MDX-xxxx>）；两支录屏读 13 帧来回好几轮，其中 9 次是为抽中某一秒的原生帧反复试探（<MDX-xxxx>）。所以一律**先粗后细 + 每轮批量抽批量读**，绝不「抽一张→看一眼→再猜下一张」。

**如果这是崩溃 / 闪退类 bug，先去第 1.5.1 节** —— 崩溃日志里有精确到毫秒的时间戳，能把下面的粗扫整段跳过。

#### 阶段 A：粗扫定位（先跑这个，帧数**硬上限 12**）
```bash
# 元信息：分辨率 + 时长（分辨率还用于第 4.7 节嵌图的真实尺寸）
ffprobe -v error -select_streams v:0 -show_entries stream=width,height \
        -show_entries format=duration -of default=nw=1 "<video>"

# 粗扫：按时长算 fps，目标 8–10 帧，宽度缩到 ~1500px（够读 UI 文字，又不爆 token）
DUR=<上面读到的秒数>
mkdir -p <scratchpad>/coarse
ffmpeg -v error -i "<video>" -vf "fps=8/$DUR,scale='min(1500,iw)':-1" <scratchpad>/coarse/c%02d.png
```
- ⚠️ **缩放用 `scale='min(1500,iw)':-1`，不要写 `scale=1500:-1`**。后者对**竖屏手机录屏是放大**（iPhone 录屏常是 828 或 1170 宽 → 被拉到 1500），文件大 3 倍、token 多烧 3 倍，却一个像素的新信息都没有（2026-09-09 实测：828×1792 的帧 50KB → 144KB）。`min()` 写法只降不升：手机录屏保持原生，桌面录屏（如 3022×1846）照常缩到 1500。
- **帧数算式：`fps = 8/时长`**，得到 8–10 帧；无论视频多长都不许超过 **12 帧**。不要再写 `fps=1` / `fps=1/3` 这类固定值 —— 186s 视频按 `1/3` 是 62 帧，按 `1` 是 186 帧，都是纯浪费。
- **一次把这 8–10 张全部读进来**（同一条消息里并列读完），用它们判断：整段流程分几个阶段、问题出在哪两帧之间。粗扫帧只用来**圈定区间**，不用来抄细节、不用来拼图。
- 这一步的产出必须是一个明确的**候选区间**，例：「问题发生在 c06(96s) 与 c07(120s) 之间」。写不出区间就说明粗扫帧不够，**再补一轮 4–6 帧的区间内粗扫**，仍然批量读 —— 而不是退回逐帧。

#### 阶段 B：区间内定点密集抽（只在候选区间里做）
```bash
# 只抽候选区间，步长 1s（区间一般 ≤20s，出 ≤20 帧）
ffmpeg -v error -ss <区间起> -to <区间止> -i "<video>" \
       -vf "fps=1,scale='min(1500,iw)':-1" <scratchpad>/fine/f%02d.png
```
- 区间跨度控制在 **20s 以内**；真的定不下来就先回阶段 A 补粗扫，**不要把步长 1s 铺到全片**。
- 密集帧同样**批量读**。到这一步应当就能写出完整的点击时间线。

#### 亚秒 / 精确到帧的取图（拼图、读倒计时数字等）
`-ss mm:ss` 只有**秒级**精度。目标画面是每秒都在变的数字（倒计时、时钟、进度）时，秒级 seek 必然要反复试 —— <MDX-xxxx> 那 9 次候选帧就是这么来的。改用下面两种写法：

```bash
# 写法 1：-ss 带小数秒（推荐，最省事）
ffmpeg -v error -ss 40.500 -i "<video>" -frames:v 1 <scratchpad>/t40500.png

# 写法 2：按帧号精确取（需要「就是这一帧」时用）
FPS=$(ffprobe -v error -select_streams v:0 -show_entries stream=r_frame_rate -of csv=p=0 "<video>")  # 如 30/1
ffmpeg -v error -i "<video>" -vf "select=eq(n\,<帧号>)" -vsync 0 -frames:v 1 <scratchpad>/n1215.png
```
- ⚠️ **一次抽一批候选点，一条命令行里抽完再一起看**，不要一张一张试：
  ```bash
  for t in 40.2 40.6 41.0 41.4 41.8; do
    ffmpeg -v error -ss $t -i "<video>" -frames:v 1 <scratchpad>/cand_$t.png
  done
  ```
  5 个候选点一起抽、一起读，一轮就能挑中；串行试探要 5 轮往返。
- 拼图 / 内嵌用的图**必须走这里重抽原生分辨率**（不带 `scale`），不能拿阶段 A/B 缩过的帧，理由见 1.7 节。

#### 多支录屏时（双端 bug 常见）
- **预算按支平摊，不是每支都给满**：两支录屏合计粗扫 ≤16 帧（每支 8）。
- 先各跑一轮阶段 A，**先判定「哪支是复现证据、哪支是对照」**，再只对复现那支做阶段 B；对照那支只需取拼图要用的那一帧。
- 没装 ffmpeg 时的降级手段：`mdls -name kMDItemPixelWidth -name kMDItemPixelHeight -name kMDItemDurationSeconds <video>` 只能拿到尺寸和时长，**读不到画面内容**，不足以写步骤。

### 步骤 3：从帧里提取这些信息，直接落进报告字段
| 从录屏读什么 | 落到哪个字段 |
|-------------|------------|
| 应用名 / 侧边栏 logo（如 `QORTEX PIM`）、菜单项 | 所属模块；⚠️ **若与用户口述的模块不一致，如实指出并让用户确认归属** |
| 面包屑 / 页面标题（如 `Catalog > Products > Xinyi001`、`Edit Product`） | 标题的「功能区 > 具体页面」分段 + 复现步骤的导航路径 |
| 地址栏 URL、环境标识 | 环境、URL。⚠️ **Web 票的 URL 是必填**（第 1 节），读不到写 `⚠️ TBD` 并追问，**不能删行**；APP 票没有 deeplink 才删行 |
| 登录用户名 / 邮箱（如 `<your-email>`） | 测试账号 |
| 状态徽标、字段值（如 `Status: Draft · Not published`） | 前置条件 |
| **鼠标位置 + 光标变化 + 每帧的画面变化 → 逐个点击动作** | **Steps to reproduce（按视频里的实际点击顺序，英文，每步一个动作）** |
| Toast / 错误提示 / 弹窗**原文** | Actual（原文照抄，不翻译） |
| 页面操作区实际有哪些按钮 | Actual 里的「实际显示了什么」对照项 |
| 分辨率（如 3022×1846 = 桌面）、是否有手机状态栏 | 平台判定（Web vs iOS/Android） |

**复现步骤写法**：按录屏时间顺序拆成编号动作，每步写清「点哪个具体元素」。同一动作反复出现（如连点某按钮 4 次无响应）要写成一步并注明重复与无响应。

**附件说明必须带时间点**，例：
```
- demo.mp4 (3022×1846, 25.7s) — 0:00–0:17 repeatedly clicking the `Scheduled` badge with no response;
  0:08 bottom action area shows only `Update Product`; 0:11 success toast; 0:23 Change History panel
```

### 步骤 4：把从录屏推断的内容标出来
录屏里**看得见**的写成事实；看不见但被推断的（如权限是在哪授予的、复现率、是否有其它入口）仍标 `⚠️ TBD`，**不要因为"视频里大概是这样"就当成已确认**。

### 步骤 5：把录屏读到的东西真正写进字段（**别读完就丢**）
读帧的目的是填字段，不是"看过了"。收尾时逐条对一遍：

- **录屏开头那段「铺垫操作」也是复现步骤**。视频里问题发生**之前**的操作（进了哪个 tab、填了什么、上一次已经出过一次同样的问题）必须进 `Steps to reproduce`，不能只写触发那一下。
  ❌ <MDX-xxxx>：录屏 0:76 帧显示用户正在 TestFlight 反馈框里写「打开 app」（说明**之前已经崩过一次**），最终票的 Steps 却只有 `Launch → Wait → Home → Wait`，前序整段丢了。
- **本会话上文已经得出的结论，直接用，不要重新从录屏推一遍**。同一次对话里若已经解过崩溃日志、已经列过时间线、已经判过哪支视频是哪端 —— 那是既有结论，进 skill 后照抄进字段即可。重新推导既慢又容易推出跟上文不一致的结果。
- 每支录屏都要在**附件说明**里有一条带时间点的描述，并说明它是**复现证据**还是**正确行为对照**。

## 1.5.1 崩溃 / 闪退类 bug（**走专用捷径，不要盲扫录屏**）

崩溃类 bug 不要从录屏画面找"哪一帧崩的" —— 崩溃日志里有精确到毫秒的时间戳，拿它反推录屏位置，抽帧量从几十帧降到 5 帧以内。

⚠️ 实测代价（<MDX-xxxx>，2026-09-03）：`.ips` 已经给出完整死锁链和 `procLaunch 18:04:32.325 → killed 18:04:45.619`，进 skill 后却又把 186s 录屏盲扫了 47 帧、思考 11m42s。**日志已经给了答案，就不要再问画面。**

**判定**：现象是 app 闪退 / 卡死被杀 / 白屏后自动退出，或用户说了「崩溃 / 闪退 / crash / 落ちる / クラッシュ」→ 走这条路线。

**动作**：
1. **先要崩溃日志再看录屏**（iOS `.ips` / Android `adb logcat -b crash -d`）。用户只给了录屏 → 先问日志，别直接抽帧。
2. 跑解析脚本：`python3 ~/.claude/skills/bug-report-formatter/scripts/parse_ips.py <crash>.ips`（多份一起传可做跨 build 比对，堆栈相同即得回归性确定值）。
3. **完整规则、字段落位、时区换算、多份日志比对、Android 侧做法 → 读 `references/crash-bugs.md`**。

## 1.6 回归 / 跨端信息（**三问都要处理过，但问法与力度分场景**）

开发打回的高频三问是「上个版本是好的吗？」「另一端是好的吗？」「这个影响使用吗？」。这三问在模板里有固定落位，未验证也要**明确写出未验证**——写出「没验」本身就挡掉了追问。

### ⚠️ 先定力度：这张票要不要**硬拦截**（先过这一步，再往下填）

⚠️ **这三问被无差别做成硬拦截，是本 skill 唯一有「用户弃用」实证的问题。**
> ❌ MDX，2026-09（内部实测）：16 分钟、票没建出来，**5 分钟全耗在争论这条规则该不该适用** —— 当时是 feature testing、pin 的分支包，没有「上个版本」可比。用户改用了别的工具。
> ❌ 另一个项目，2026-09（内部实测）：非回归期的普通票也照样出 `Regression: ⚠️ TBD not verified (derives from a new requirement…) | iOS: ⚠️ TBD not verified` —— 纯噪音。

**硬拦截只在这一种情况成立：这张 bug 属于某轮版本回归**。判定看**这张票要挂到哪**（团队的提法：按 bug link 票的情况自动判断）：

| 信号 | 力度 |
|------|------|
| 用户给的 link 目标是**回归总票**（`[QA] ... Regression Testing` 之类），或用户说了「这个版本的回归 / 挂总票 / regression」 | **硬拦截**：前两问建票前必须有确定值 |
| link 目标是**普通需求票 / 功能票**，或没有 link 目标 | **不拦截**：能填就填，填不了写 `⚠️ TBD`，或按下面「无参照物」规则删行。**照常出报告、照常建票**。追问时**只保留「另一端是否也有问题」一问**（团队提议的简化，2026-09-03），「上个版本」那问不主动追 |
| 明确是 **feature testing / 单独打的分支包 / 新需求验收** | **不拦截，且「上个版本」那一问直接不问**——没有可比基线，问了也答不出。回归行写 `N/A (feature testing on a branch build, no baseline)` 或整行删掉 |
| 明确是**新需求引入的问题**（不是老功能坏了） | 同上，`derives from a new requirement` 这种话不要写成 `⚠️ TBD`，要么写成确定值 `Not a regression — new requirement`，要么删行 |

- 🔴 **不许为了这三问阻塞出报告**。硬拦截的含义是「B 模式建票前把值补齐」，**不是**「答不出就不给报告」。硬拦截场景下用户明确说「不验，按未知开」→ **立刻放行**，不要再劝第二次。
- 拦截力度判断不了 → 按**不拦截**处理，并在结尾用一句话问「这张要挂当期回归总票吗」，一次问完。宁可少拦一次，也不要再出现 5 分钟争论规则的情况。
- 项目文件（`projects/<KEY>.md`）里写的「回归期硬拦截」，**其适用范围同样受本节约束** —— 它管的是「回归期的票」，不是该项目的所有票。

| 字段 | 取值 | 说明 |
|------|------|------|
| 上个版本是否正常 | `是（已在 <版本号> 验证正常）` / `否，<版本号> 已存在` / `⚠️ TBD 未验证` | **仅适用于有版本号体系的项目**；无版本号的项目改问「是否新出现」，见下 |
| 另一端是否复现 | `Android 正常，仅 iOS 复现` / `iOS 同样复现` / `N/A（Web 票）` / `⚠️ TBD 未验证` | 双端项目必写 |
| 是否阻塞使用 | `阻塞` / `有 workaround：<绕过方式>` / `不影响使用，可 can-be-ignored` | 直接进优先级依据 |

### ⚠️ 先判断这个项目有没有「版本号体系」，再决定回归那一项怎么问
「上个版本是否正常」预设了存在可指名的 build / release 号。**持续部署的 Web 项目没有这个东西**，硬写一行 `Regression: ⚠️ TBD` 既指不出「上个版本」是哪个、也不给开发任何信息，纯属噪音——反而违背了「写 TBD 是为了挡追问」的初衷。

判断方法：APP 票 / 项目文件里写了版本号体系 / 票上 `versions`·`fixVersions` 字段在用 → **有**；持续部署的 Web（如 KGM 这类 `*.qorcommerce.com` 环境，版本字段常年为空）→ **无**。

| | 有版本号体系（APP、带 release 号的 Web） | 无版本号体系（持续部署 Web） |
|---|---|---|
| 问法 | **上个版本是否正常** | **是否新出现** |
| 取值 | `是（已在 <ver> 验证正常）` / `否，<ver> 已存在` / `⚠️ TBD 未验证` | `Newly appeared（<日期/上次测试> 时正常）` / `Long-standing（一直如此）` / `⚠️ TBD 未验证` |
| 参照物 | release / build 号 | **某次「验证通过过」的日期** |
| 拿不到时 | 写 `⚠️ TBD 未验证`，**保留该行** | 确实无从判断（首次测这块、没有历史结论）→ **整行删掉**，不要留一个指不出参照物的 TBD |

⚠️ **「可比时间点」只能是「那时候是好的」的日期，不能是「发现 bug 的日期」。**
`first observed 2026-04-03` 这类写法是**假参照物**——它对「之前是好的还是一直坏的」零信息量，属于本节明令要删的噪音；不要因为句子里带了个日期就以为满足了条件。手上只有发现日期 → **删行**。

无版本号项目的回归行写法示例：
- ✅ `Regression: Newly appeared — was OK on 2026-03-20 regression run.`（参照物 = 那次验证通过）
- ✅ `Regression: Long-standing — also reproducible before the 2026-04 deploy.`
- ✅ `Regression: ⚠️ TBD — this area was last verified OK on 2026-03-20, not re-checked since.`（参照物成立，只是没复验）
- ❌ `Regression: ⚠️ TBD — first observed 2026-04-03, not checked against an earlier deploy.` —— **发现日期不是参照物**，这行该删掉，而不是这么写

- 我自己测出来的 bug：能顺手在另一端 / 上一版本验一下就验，验了写结论，没验写 `⚠️ TBD 未验证`，不要凭印象填。
- 用户口述的 bug：这三项**在结尾追问里逐条列出**，但不阻塞报告输出——先出报告，把 TBD 标清楚。
- 回归期（**确实挂着某个版本回归总票**）时，前两项升级为硬追问项：B 模式建票前必须有确定值。力度判定见本节开头那张表，**不要跳过它直接套用这一条**。
- ⚠️ **APP 项目常有两套版本号**：build 号（四位数、两端各自递增，如 iOS `1739` / Android `1362`）与 release 版本（三段式、两端共用，如 `5.5.60`）。
  **标题的平台段写 build 号，回归行写 release 版本**。用户只给一个：四位数 → build；带两个点 → release；分不清就问，别混用。
- 回归行的措辞**优先套用项目里已有的说法**（例：`Also reproducible on version 5.5.50.`），没有既有说法才用下面的通用格式。
- ⚠️ **「三问都要处理过」不等于三行都必须留在正文里**。跨端那项 Web 票写 `N/A`；回归那项在「无版本号项目且无参照物」「feature testing / 分支包」「新需求票」这三种情形下**删行**（见本节开头的力度表）。真正不许发生的是「压根没想过这三问」，不是「少了一行字」——**更不是「答不出就不给报告」**。

## 1.7 证据图（**有录屏 / 双端 bug 时必做**）

录屏本身不算证据到位——读者得拖进度条才能看到问题。必须补静态图：

| 什么时候 | 做什么 |
|---------|--------|
| 有录屏 | **before / after 拼图**，放在视频上方；视频仍要完整嵌入，不用截图替代 |
| iOS + Android 都涉及 | **每个场景一张左右对比图**（iOS 左、Android 右），不要贴两张独立图片 |
| 任何拼图 | **每侧标 `OS(设备) · build · 时间点`**（团队建议，2026-09-03：方便开发知道哪个录屏对应哪台设备）；**红框圈出问题部位**（团队反馈，2026-09） |

三条铁律：
- **原生像素粘贴、绝不为了等高而缩放**（重采样会让 UI 文字发虚）。拼图要用的帧**按 1.5 的亚秒写法重抽原生分辨率**，不能拿粗扫时 `scale` 缩过的帧。
- **圈注画在原生尺寸的图上再拼接**，框线宽度随分辨率放大（手机 3–4px、桌面 8–10px），否则缩略后看不见。
- 圈的是**现象**不是结论：框住「显示 `580分50秒` 的那块」，别在图上写「计算错误」。

现成脚本（省得每次现写 Pillow）：
```bash

  --out combined.png --title "<场景>" \
  --left  ios.png     --left-label  "iOS 1766 · 0:49" \
  --right android.png --right-label "Android 12 (Pixel 4 XL) · 1373 · 0:49" \
  --left-box 1085,240,1470,320 --right-box 1740,205,1900,255 --arrow
```
**完整规则（拼接细节、降级路径、Pillow 用法、字体陷阱、多 Case 的证据块）→ 读 `references/evidence-images.md`。**

## 2. 优先级判定（必须附依据）

按**用户影响面**和**功能重要性**判定，二者取**较高**的一档。输出时必须写一行 `依据：...`。
（本节标准更新自团队 Bug Priority Definition，2026-09-03：新增 **Lowest** 档；法务/合规/金额正确性一律 Highest；「有 workaround 的主功能问题」明确落 Medium。）

| 优先级 | 判定标准 | 典型例子 |
|--------|---------|---------|
| **Highest** | 影响 **>50%** 用户，或**完全阻断核心业务功能**，**或涉及任何法务 / 合规 / 金额正确性问题（与影响用户数无关）** | 系统宕机；结账/登录/注册完全不可用；所有支付方式均失败；**税额 / 价格 / 折扣 / 运费 / 积分或优惠券金额错误**；其它违反法规的内容 |
| **High** | 影响 **10–50%** 用户，或**严重影响主要功能** | 某常用支付方式不可用；多个地区结账中断；关键数据丢失 |
| **Medium** | 影响 **1–10%** 用户，或影响**次要功能**，**或主功能异常但仍有可用的 workaround** | 仅特定浏览器/设备复现；功能可用但体验降级；订单历史未即时更新；**用户可见界面缺少翻译** |
| **Low** | **轻微功能问题**：行为不正确，但用户仍能完成任务——受影响功能属边缘功能，或存在绕过方式。约 **<1%** 用户 | 输入框只能逐字符输入；限购选项被隐藏而非置灰；banner 数据陈旧、重进页面才刷新；管理员看不到自己操作的完整审计日志；**早于本版本就存在的跨端行为差异（Web vs App、iOS vs Android）且不阻碍用户完成任务** |
| **Lowest** | **纯视觉 / 纯文案**，不影响任何用户操作。**包含一切与设计稿的差异**，只要没有功能依赖它 | 颜色 / 字重 / 间距 / 圆角 / 换行与设计稿不一致；分割线缺失；静态文案错别字或漏空格；同一页面 Web 与 App 看起来不同但功能无差异 |

判定要点：
- **法务 / 合规 / 金额正确性优先于影响面**：命中即 **Highest**，不因「只有一个用户遇到」下调，也不因有 workaround 下调。
- **数据丢失 / 安全与隐私泄露** → 至少 **High**，即使命中用户少。
- **有 workaround**：主功能问题 → 落 **Medium**（不再一律「下调一档」）；次要 / 边缘功能问题 → 落 **Low**。依据里必须写明 workaround 是什么。
- **功能 vs 视觉的分界**：只要有任何用户操作被影响（点不动、看不到必要信息、需要额外步骤）→ 最低 **Low**；完全不影响操作的外观 / 文案差异（含设计稿走查出的偏差）→ **Lowest**。
- 影响面数据缺失时，用「受影响的入口/平台占比」保守估算，依据里写清估算方式（例：「仅 iOS 单端 + 仅优惠券入口 → 估 <10% → Medium」）。
- **回归 vs 既存**（来自第 1.6 节）：确认是**本版本新引入的回归**（上个版本正常）→ **上调一档**，依据里写明「上个版本 <ver> 正常，本版本回归」；确认是**老版本已存在的既存问题** → 不上调，依据里写明。`⚠️ TBD 未验证` 时不作调整，依据里注明「回归性未验证」。
  ⚠️ 两个例外：**纯视觉 / 纯文案（Lowest）不因回归上调**，除非它同时构成设计稿之外的功能影响；**早于本版本的跨端差异**按上表落 **Low**，不算回归。
  **无版本号体系的项目**用时间点代替版本号：「2026-03-20 回归时正常，本次新出现」同样按回归**上调一档**；判不出新旧就当既存处理，依据里写「新旧未判定」，不要因为缺版本号就跳过这一档判断。
- **不影响使用 / can-be-ignored**（用户明确判定不影响主流程）→ 有操作影响落 **Low**、纯外观落 **Lowest**，依据里带上绕过方式。
- 依据格式：`依据：影响范围 <X> + 功能重要性 <Y>（<有/无> workaround）+ <回归/既存/回归性未验证> → <档位>`

> 若目标 Jira 项目用的是 Severity（Critical/Major/Minor）而非 Priority，映射：Highest→Critical，High→Major，Medium/Low/Lowest→Minor，并同时给出两者。

## 3. 输出格式（标准报告）

### 标题（**必须英文**）
`[<Module>] <one-line problem>`

带环境/平台维度的项目（如需与既有票风格一致）用面包屑式：
`<环境> > <平台(版本)> > <功能区> > <具体模块/页面/条件> > <问题>`

规则：
- **必须写出「具体出问题的模块/页面」**，别从大区域直接跳到问题。
  - ✅ `STG > iOS(645) > Checkout > Coupon change modal > Category coupons are listed in a different order than Web/Android`
  - ❌ `STG > iOS(645) > Coupon change modal shows coupons in a different order`（少了功能区分段）
- **标题保持简洁**：测试账号、地址、邮编、商品 code、订单号等**具体数据一律放进复现步骤**，不写进标题。
- 平台段写法：Web = 只写区域不带平台；单端 = `iOS(<环境版本>)` / `Android(<环境版本>)`；双端 = `Android(<ver>)/iOS(<ver>)`。**APP 票的版本号是「发现问题时的环境版本」，不是修复版本**；没有就问用户。
- 平台判定：鼠标 hover/光标/桌面布局 → Web；APP 专属交互/崩溃 → iOS/Android。不确定就问。
- ⚠️ **分隔符必须是字面 `>` 字符，绝不能 HTML 转义**。在 `summary` 里写 `&gt;` 会让 Jira 存下字面五个字符 `&gt;`（summary 是纯文本字段，不是 HTML）——<JMA-xxxx> 上实测踩过，2026-07-28。`&amp;` / `&quot;` 同理，直接写 `&` / `"`。

### 正文模板

```
**所属模块 / 平台：** <模块> / <Web | iOS | Android>
**优先级：** <Highest | High | Medium | Low | Lowest>
依据：影响范围 <…> + 功能重要性 <…>（<有/无> workaround）→ <档位>

**环境：**（必填集按平台，见第 1 节的表；必填项缺失写 ⚠️ TBD，不删行）
- 环境：<PRD / STG / DEV>                        ← 必填
- App 版本：<iOS App 645 | Android App 309>      ← **APP 票必填**；Web 票删掉此行
- 设备 / OS：<iPhone 15 Pro / iOS 17.5>          ← **APP 票必填**；Web 票删掉此行
- 浏览器：<Chrome 126>                            ← **Web 票必填**；APP 票删掉此行
- URL：<出问题的页面链接>                          ← **Web 票必填**；APP 票有 deeplink 才写
- 以下选填，**有就写、没有就整行删掉，不要留空、不要追问**：
- 测试账号：<…>
- 网络：<Wi-Fi / 4G>

**回归 / 跨端：**（三问都要处理过；未验证写 ⚠️ TBD 未验证，删行只有 1.6 节列的那一种例外）
- 上个版本是否正常：<是（已在 644 验证正常）| 否，644 已存在 | ⚠️ TBD 未验证>
  ← 无版本号体系的持续部署项目改问「是否新出现」，参照物用日期：<Newly appeared（2026-03-20 时正常）| Long-standing | 无可比时间点则整行删掉>，见 1.6 节
- 另一端是否复现：<Android 正常，仅 iOS 复现 | iOS 同样复现 | N/A（Web 票）| ⚠️ TBD 未验证>
- 是否阻塞使用：<阻塞 | 有 workaround：<绕过方式> | 不影响使用，可 can-be-ignored>

**前置条件：**
- <初始状态、账号权限、数据准备…>

**Steps to reproduce:**（**必须英文**）
1. …
2. …
3. …

**Actual:**（英文）
<实际发生了什么；含错误码 / 提示原文>

**Expected:**（英文）
<应该发生什么>

**附件：**
- <文件名> — <这张图说明什么>

**备注：**
<补充信息、影响范围、疑似关联票、风险提示>
```

**Actual 在 Expected 之前**（团队约定，2026-08）：读者先看到「哪里坏了」，再看「本该是什么」。两份 skill 早期写法不一致，以此为准。

**复现步骤重写规则**：编号、每步一个动作、**可被他人独立复现**（含具体入口、点击对象、输入数据）。口语里的「然后就那样了」要拆成可执行动作；拆不出来的部分标 `⚠️ 待补充`。

```
**Case 1 - <条件，如 in-place upgrade 5.5.50 (1712) -> 5.5.60 (1723)>:**
<带 mm:ss 时间点的 bullet 时间线>

**Recording:**  <录屏>

**Case 2 - <另一个条件，如 no upgrade, leave and re-enter the menu>:**
… 同样三部分 …
```

编号统一用 `Case 1` / `Case 2`，并从 `Actual:` 的 bullet 里引用这些标签，让读者能把每条结论对上对应证据。

### 自检（输出前必过）
1. 必填字段齐全（复现步骤、预期/实际、按平台的环境必填集、回归/跨端三行），缺失项都已用 `⚠️ TBD` 标出。
2. **标题、Steps to reproduce、Actual、Expected 全部是英文**。
3. 标题符合格式，且含「具体模块/页面」。
4. 优先级带判定依据。
5. 复现步骤他人可独立复现，无「同上」「那个页面」等指代。

7. 环境部分：该平台的**必填行一行不缺**（拿不到的写 `⚠️ TBD`），选填行无值的已整行删掉，没有空占位行。
8. 回归/跨端三问都处理过，**且力度按 1.6 节开头那张表判过**（跨端 Web 写 `N/A`；回归项在无版本号且无参照物、或 feature testing / 分支包 / 新需求票时按 1.6 节删行，其余情况必须在），且优先级依据里体现了回归 / 既存 / 未验证的判断。
9. 有录屏时：已抽帧看过，步骤按视频里的实际点击顺序写，附件说明带时间点，且已按 1.7 节补了 before/after 拼图（双端 bug 补左右对比图）。
   - 抽帧走的是 **1.5 两阶段**（粗扫 ≤12 帧 → 区间内密集），**没有逐帧线性扫**。
   - 拼图每侧都标了 **OS(设备) · build · 时间点**，并且**用红框圈出了问题部位**（1.7 C）。
10. **用户给的每一份素材都用上了**（1.4 A）：单端 bug 的另一端素材作为「正确行为对照」附上，附件说明写清了每份的角色；被弃用的素材都单独说明过理由。

13. 没有把已经确定的事再问一遍（1.4 C），抛出的选项都是单一维度（1.4 B）。
14. 无对开发的评价、无臆造信息。
15. 可直接粘进 Jira，无需二次排版。

## 4. 建票模式（B）—— 通用 Jira 流程

> 不绑定任何具体项目。**项目 key、站点、经办人、优先级默认值都从用户处确认，不硬编码。**

### 4.1 确认目标
- **项目 key**：优先看本 skill 的 `projects/<KEY>.md`（见第 0 节）；其次看当前工作目录的项目级 skill / CLAUDE.md；都没有就**问用户**（要 key，如 `ABC`；注意项目**显示名 ≠ key**）。命中项目文件时，站点 / cloudId / 必填字段 / Priority 取值都直接用文件里的，不再探测。
- **站点 / cloudId**：`mcp__claude_ai_Atlassian__getAccessibleAtlassianResources` 取；多站点时问用户。
- **issueType**：`Bug`（项目无此类型则用 `getJiraProjectIssueTypesMetadata` 查实际可用类型）。

### 4.2 查重（**写文案之前先做**）
⚠️ **顺序很重要**：抽完帧、搞清现象之后**立刻查重**，不要等文案写完再查——命中老票的话整段文案就白写了。

**查重一律走 curl + jq，不用 `searchJiraIssuesUsingJql`。** 原因：那个 MCP 工具的 `fields` / `maxResults` 参数不生效，照样返回整个 GraphQL 节点（实测 84k–362k 字符），必然超 token 上限被落盘，再补一轮 Bash+jq 才拿到结果 —— 一次调用中位 7.5s、最慢 26s，一次开票查 2–5 次就白烧 30–90 秒和好几个模型回合。curl 直取字段 0.2s 出结果。

```bash
# 认证：与 4.6 同一套（memory 里的 jira-credentials）
# ⚠️ token 必须按反引号精确提取。memory 里那行常带中文注释，形如
#    - API token: `ATATT…`（2026-08 更新）
#    用 sed 's/.*API token: *//' 会把注释一起吃进去，AUTH 必然 401。
# ⚠️ 标签大小写和冒号都不固定！实测 memory 里写的是「- API Token：`...`」
#    —— 大写 T + **全角冒号**。写死 'API token: ' 会取到空串，然后 base64 出一个
#    只有邮箱的 AUTH，照样 401，且长得像「token 过期」，极易误判（2026-09-09 实测）。
#    所以正则要同时容忍大小写与全/半角冒号：
TOKEN=$(sed -n 's/.*[Tt]oken[：:] *`\([^`]*\)`.*/\1/p' <memory-file> | head -1)
[ -z "$TOKEN" ] && echo '❌ token 没取到 —— 先 grep -i token <memory-file> 看实际写法，别当成过期'
AUTH=$(printf '<email>:%s' "$TOKEN" | base64 | tr -d '\n')
echo "$AUTH" > /tmp/jira_auth && chmod 600 /tmp/jira_auth
# 先自检认证，别等查重返回空数组才发现是 token 问题（空结果和无命中长得一样）
curl -s -o /dev/null -w 'auth: %{http_code}\n' "https://<site>/rest/api/3/myself" -H "Authorization: Basic $AUTH"
Q='project = <KEY> AND summary ~ "<关键词>" ORDER BY created DESC'
curl -s -G "https://<site>/rest/api/3/search/jql" -H "Authorization: Basic $AUTH" \
  --data-urlencode "jql=$Q" --data-urlencode 'fields=summary,status,created,reporter' \
  --data-urlencode 'maxResults=20' \
| jq -r '.issues[] | [.key, .fields.status.name, (.fields.created[0:10]), .fields.reporter.displayName, .fields.summary] | @tsv'
```
- 多个关键词**一次 curl 一条 JQL**，用 `OR` 拼（`summary ~ "A" OR summary ~ "B"`），别拆成多次调用。
- **日文票要同时搜英文措辞、英文票同时搜日文**：历史上漏判过两次重复票 —— `レイアウト崩れ` 漏了标题写成 `The layout is broken.` 的 <KGM-xxxx>，`複数回/連打` 漏了写成 `Double-click` 的 <KGM-xxxx>。至少覆盖：UI 文案原文 + 对应英文动词/名词。
- 命中面太窄时把 `summary ~` 换成 `text ~`（搜正文与评论），但仍只取上面那几个 field。
- 关键词取「模块 + 现象」里最独特的那个词（UI 文案原文往往最准，如 `指定時間より前の受け取り`），不要用长句。
- **关键词不要带平台段**（`iOS` / `Android`），否则会漏掉标题只写另一端的老票。
- **同一版本回归期内最容易开重复票**：截断 / 溢出 / 布局错位 / 连点这几类现象在一轮回归里常出现多次（实测某次回归 `truncated` 出现 3 次）。这几类**必须先搜再写文案**。
- 只有在没有 token / curl 不通时才退回 `searchJiraIssuesUsingJql`，并预期要落盘 + jq。

**⚠️ 先搜窄的，别一上来全项目扫**（团队提议，2026-09）。用户给了 link 目标票时，重复票**几乎总在那张票的关联范围内**——同一个需求 / 同一轮回归下开的票。全项目扫一次常返回几十条再人工筛（实测 51 条命中筛出 2 张近亲票），纯浪费。

顺序（**第 1 步命中就够了，不必再跑第 2 步**）：
```bash
# 第 1 步：只搜 link 目标票的关联范围（用户给了 link 目标 / 回归总票时走这个）
Q='issue in linkedIssues("<LINK目标票>") AND summary ~ "<关键词>" ORDER BY created DESC'
# 回归期同理，把 <LINK目标票> 换成当期回归总票号 —— 同一轮回归的票全挂在它下面

# 第 2 步：第 1 步没命中、或压根没有 link 目标时，才放开到全项目
Q='project = <KEY> AND summary ~ "<关键词>" ORDER BY created DESC'
```
- `linkedIssues()` 只覆盖一层关联，够用；它返回空**不等于没有重复票**，所以第 1 步无命中必须补跑第 2 步。
- 没有 link 目标票 → 直接第 2 步，不必假装有范围。

- **命中疑似重复 → 立刻停下来报给用户**，别继续写文案。列成表格：票号 / 状态 / 标题 / 对应本次的哪个现象，并给出选项：
  1. 不新建，把本次复现（新版本号 + 录屏）追加为老票评论；
  2. 新建一张合并票，relates to 老票；
  3. 按现象拆多张。
  同时给出你的建议（老票仍 Open 且是同一处逻辑 → 建议选 1）。用户定了再往下走。
  ⚠️ **这是 4.3 那道关卡的一部分，不是额外一轮**：把查重结论和文案草稿**放在同一条消息里**抛出（见 4.3），别先问一次「要不要继续开票」、写完文案再问一次「可以建票吗」——实测被点名为「人工对话确认次数过多」（内部反馈，2026-09）。
- 没命中 → 直接进 4.3。

### 4.3 唯一确认关卡：文案 + 字段 + 查重结论一次性抛出
**只设一道关卡**，不要「先确认文案、再确认草稿」分两轮——用户通常在第一条消息里就把票的字段（项目、经办人、link 目标）一起给了，拆两轮纯属浪费往返。

一次性输出：Title / Description 全文 + 一行 Jira 字段 + 查重结论。用户回「确认」就直接执行 4.5 起的写操作。

**B 模式的 description 用下面这个精简版**（不是第 3 节那份完整模板）——只保留会真正进 Jira 正文的部分：环境一行 + Steps / Actual / Expected（+ 可选 Note）。**优先级依据、附件清单、前置条件、所属模块这些不写进 description**，它们走 Jira 字段或放在关卡②的草稿里。

输出格式**照抄这个骨架**：

```
Title
<环境> > <平台(版本)> > <功能区> > <具体模块/页面（可带日文原文，如 Delivery time selection modal (配達時間の選択)）> > <问题>

Description
Environment: <STG-2 (iOS) | PRD (Web) | …>

**Steps to reproduce:**
1. …
2. …
3. …

**Actual:**
<实际发生了什么；UI 文案原文照抄，如 本日 07月28日(火)>

**Expected:**
<应该发生什么；可引用参照物，如 "the same as on Web (see the Web screenshot)">

Regression: Worked on <release ver>; new in <release ver>. / Also reproducible on version <release ver>. / Not verified on <release ver>. | <另一端>: OK / same issue / not verified / N/A

Requirement source: <Slack thread | Figma design | Confluence page | KEY-123>   ← 有需求出处就必出，且必须是可点的链接

Note: <可选。只在需要划定范围 / 排除误解时写一句，如「日期已经是粗体，只有时段没有」>
```

规则：
- `Title` / `Description` 两个裸标签**单独成行、不加粗**，后面直接跟内容。
- 🔴 **需求来源写进 description，不要放评论**（内部实测，2026-09）。
  > ❌ 反例：正文写 `Note: Requirement source — Slack (link in comments).`，链接扔在评论里。用户原话：「放在 comment、而且不是 link 格式，不方便查需求；如果是链接格式放在 description 会方便一点」——最后她手动搬进了描述。
  - 位置：`Regression:` 行之后、`Note:` 之前，标签固定写 `Requirement source:`。
  - 必须是**可点的链接**——走 API 建票时裸 URL 是纯文本，**必须补 `link` mark`**（见 `references/jira-mechanics.md` §4.7.1），这条最容易忘。
  - 超长的 Slack / Figma URL 用短标签（`Slack thread` / `Figma design`），href 放完整 URL（同上参考文件 §4.7.1）。
  - 出处是另一张票（`KEY-123`）→ 正文照样补 link mark，**并且**在 4.8 建一条 issue link，两件事都做。
  - 只在真的有需求出处时出这一行，没有就整行删掉——不要写 `⚠️ TBD`。
- Steps / Actual / Expected **必须英文**（**Actual 在 Expected 之前**）；UI 文案、地址、邮编、商品 code 原文照抄。
- 多条复现路径 → 按第 3 节的 `Case 1` / `Case 2` 拆开，各带自己的证据块。
- Environment 只写一行，但**该平台的必填项都要并进这一行**（Web：环境 + 浏览器版本 + URL；APP：环境 + App 版本 + 设备/OS）；账号、网络等选填项有必要才写。
- `Regression:` 行内容取自第 1.6 节（英文）；Web-only 项目省掉后半段 `| Android: …`。「是否阻塞使用」不进 description，走优先级依据。
  **该行在有版本号体系的项目里必出**；**无版本号体系的持续部署项目**改用 `Newly appeared / Long-standing` 措辞并以日期为参照，**连可比时间点都没有时整行删掉**——别留一个指不出参照物的 `⚠️ TBD`。
- Note 是可选行，没有就整行删掉。
- 给完文案后，用一行把待确认的 Jira 字段一起抛出，例：
  > 确认这两段文案 OK 吗？（Jira 那边：<KEY> / Bug / <优先级> / assignee <姓名> / 新票 blocks <KEY-123>，附上 <附件列表>）
- 紧跟一行优先级依据；有查重命中就把 4.2 的结论表也附在这条消息里。**这条消息发完就等用户点头，不要再追加第二道草稿关卡。**

### 4.4 收集字段（在 4.3 之前就备好，不单独占一轮对话）
- **优先级**：按第 2 节判定，**带依据一并给出**；用户可覆盖。
- **经办人**：项目文件有规定就用它；否则**默认指给报告人自己（当前用户）**，在 4.3 关卡里作为默认值抛出、用户可改——多数 QA 项目就是自指派，默认成「问用户」纯属多一轮往返。要指给开发时才按名解析：优先用项目文件里的 accountId 表，没有再 `lookupJiraAccountId`（同名多人时列出让用户选；排除 `accountType: customer`）。
  ⚠️ 大站点里近似同名账号很多（`Foo Bar` / `Foo Baz` / `Fool Bar`），**绝不能用 `user/search` 的第一条结果直接指派**。
- **链接**：用户给目标票号时，默认「新票 **blocks** 目标票」；其它关系需用户明说。
  🔴 **用户给过任务票 / 需求票链接 → 建完票直接 link，不要再问一遍、更不要漏做**（内部实测，2026-09-03：「已经给了任务票链接，希望可以开完票后直接帮我 link」）。link 目标在 4.3 那条确认消息里作为默认值一并抛出（例：`新票 blocks <KGM-xxxx>`），用户不改就照建。**建完票必须走 4.8，把它当成建票流程的一部分，不是可选收尾。**
  **回归期**：新 bug 默认挂当期回归总票，关系按范围区分——**本次改动范围内的问题 → `Blocks`；范围外顺手撞到的 → 项目里的「发现关联」类型（如 `Discovery - Connected`），没有该类型就 `Relates`**。判断不了就问用户。
  **回归总票号一律现查、不猜**（按项目文件给的命名规则跑一条 JQL，取最新那张进行中的），查到后连票号带标题一起给用户确认。
- **附件**：以用户拖入图片自带的 source 路径为准；**贴哪些传哪些、按贴入顺序**，不去扫文件夹里的其它文件。视频不能预览，让用户给路径。
- **可选字段（components / labels / fixVersions / Severity）：默认不填、也不要问**。项目文件有规定才填；没规定又觉得该填 → 先看这个项目近 50–100 张 bug 的实际使用率，几乎没人填就跳过。别为一个团队根本不用的字段占用户一轮回答。

### 4.5 创建

⚠️ **建票前先确认该项目 Bug 的必填字段**（不同项目不一样，例如有的项目 `reporter` 是必填，漏了直接报错）：项目文件里写了就照用；没写就跑一次
`/rest/api/3/issue/createmeta?projectKeys=<KEY>&expand=projects.issuetypes.fields` → 取 `required: true` 的字段名，一次性备齐再建。

`mcp__claude_ai_Atlassian__createJiraIssue`：cloudId / projectKey / issueTypeName=Bug / summary / description（`contentFormat: markdown`，加粗用 `**…**`、有序列表用 `1.`）/ `assignee_account_id` / `additional_fields: {"priority": {"name": "<档位>"}}`。记下返回的 key。

⚠️ **必填字段兜底**：报错说缺必填字段（Severity / Component / Found-in-version 等）→ 用 `getJiraIssueTypeMetaWithFields` 查该 issuetype 的必填字段，把缺的列给用户补值，用 `additional_fields` 带上重试，别干等报错。

#### 4.5.1 建票失败 / 卡住 → 读 `references/jira-mechanics.md`
建票是唯一有副作用的一步。**失败时第一件事永远是确认票到底建没建成**（跑一条 `reporter = currentUser() AND created >= -1h` 的 curl），建成了就直接进 4.6，**绝不重建**。错误分类、MCP 挂起、token 过期的分流细节见参考文件。

### 4.6 上传附件 · 4.7 内嵌正文 · 4.7.1 补 link mark → 读 `references/jira-mechanics.md`

这三步的机制细节（去音轨命令、压缩阈值与近无损瘦身、Jira 附件上限实测、ADF `mediaSingle` 靠左 + 真实尺寸、裸 URL / 票号补 `link` mark 的正则与陷阱）都在参考文件里。**走到这三步时读它**。

必须记住的四条铁律（违反了后面全白做）：
- **视频一律去音轨**，与压不压无关；**≤50MB 传原文件**（同站点实测 32.2MB 成功）。
- **「上传附件」和「正文里出现这张图」是两件事**：走 API 必须分两步，只上传的话图只躺在 Attachments 面板里。**用户说「放进去 / 内嵌 / 嵌进去」= 要内嵌**；给了截图/录屏就默认内嵌，不要问。
- **改正文前先 GET 读回，每次 PUT 前都重新 GET**，别拿旧副本把别人刚拖的附件冲掉。
- **正文里的裸 URL 和票号必须补 `link` mark**，API 建票不会自动识别，不补就点不动（需求来源那条尤其容易忘）。

### 4.8 链接
`getIssueLinkTypes` 查类型 → `createIssueLink`。⚠️ inward/outward 容易反，**建完读回 `fields=issuelinks` 校验方向**，反了删掉重建。
- 校验时读**目标票**的 `issuelinks` 更直观：`<type> ← <新票>` 表示新票在 inward 侧（即「新票 blocks 目标票」，正确）；`<type> → <新票>` 说明方向反了。
- 拿不准某个关系在本项目怎么用 → 读一张同类老票的 `issuelinks` 照着建，比猜语义可靠。

### 4.9 汇报
票号 + URL ✓ / 标题 / 优先级（含依据）/ 经办人 / 状态 / 链接方向（已校验）/ 嵌入了哪些文件 / 失败项。

**顺手记一行耗时基线**（团队提议，2026-09，照 iOS 打包耗时基线那个模式，此前一直没落地）。写进 `~/.claude/projects/<project-dir>/memory/issue-writing-elapsed-baseline.md`，每开一张票追一行：
```markdown
| 日期 | 票号 | 素材 | 抽帧数 | 耗时 | 备注 |
|------|------|------|--------|------|------|
| 2026-09-03 | <MDX-xxxx> | 2 视频 43MB | 13 | ~17min | 逐帧试探 9 次；两道确认关卡 |
| 2026-09-03 | <MDX-xxxx> | 1 视频 186s + 2 .ips | 47 | ~12min | 未走崩溃日志捷径 |
```
- **有基线才看得出改动有没有用**。上面两行是改造前的实测值，改造后同类票应当落在「崩溃票 ≤5 帧」「普通录屏票粗扫 8 帧 + 密集 ≤20 帧」。
- 明显超出基线（如抽帧数 > 30、耗时 > 20min）→ 在汇报里点出来是哪一步卡住了，别默默吞掉。
- 这个文件只追加、不重写；**不要**把它当成必做项去阻塞流程，写不上就算了。

**中途失败兜底**：票在 4.5 就已创建，若 4.6–4.8 失败**不要重建票**——汇报里带上已建票号 + 卡在哪一步 + 原因，告知可从该步重跑（上传/嵌图/链接均幂等，重跑前先读回当前状态避免重复）。

## 5. 边界与限制
- 不臆造未提供的信息；缺关键字段提示或追问，不编造。
- 优先级判定必须附依据，避免主观随意。
- 客观描述现象，不夹带对开发的评价，不下结论式归因。
- **进 skill 第一步先按第 0 节自行分流（JMA 回归 / 通用），并在开场一行说明走的哪条路线**；信号缺失默认通用路线，只在信号矛盾时才问用户。
- A 模式不做任何 Jira 写操作；B 模式**先查重、再一次性确认（文案 + 字段 + 查重结论）**，用户点头才写 Jira。只设这一道关卡，不拆两轮。
- **回归/跨端三问（1.6 节）与按平台的环境必填集（1 节）都要被处理过**：拿不到就写 `⚠️ TBD`，不要静默删行——这两类缺失是开发打回的最高频原因。
  但**「处理过」≠「硬拦截」**：三问的力度按 1.6 节开头那张表定，**只有挂回归总票的票才硬拦截**；feature testing / 分支包 / 新需求票不拦截，且没有可比基线时回归那一项直接删行。**任何情况下都不许因为这三问答不出而不给报告。**
  另一处删行例外：**无版本号体系的持续部署项目**，回归那一项在连可比时间点都没有时删行（1.6 节）——一个指不出参照物的 TBD 不挡追问，只是噪音。
- 附件**清晰度优先**：≤50MB 直接传原文件，只在 >50MB 时压且用原生宽度 + 低 CRF（`references/jira-mechanics.md` §4.6.0；≤50MB 但 >15MB 可选近无损瘦身）；压后不可读或压缩率不划算就传原文件，绝不覆盖用户原文件。**视频一律去音轨**，与压不压无关。
- 媒体**必须内嵌进正文/评论**（§4.7），不能停在「上传成 attachment」；靠左 + 原生尺寸；改正文前先 GET 读回，别把用户刚拖的附件冲掉。
- 正文里的**裸 URL 和票号必须补 `link` mark**（§4.7.1，正则与陷阱在 `references/jira-mechanics.md`）——API 建票不会自动识别，不补就点不动。
- **需求来源写进 description、且做成可点链接**（4.3），不要扔在评论里。
- **用户给的素材默认全部用上，skill 的默认规则不得静默丢弃它们**（1.4 A）；抛给用户的选项必须是单一维度（1.4 B）；已经确定的事不问第二遍、但仍要落进字段（1.4 C）。
- **抽帧必须两阶段、批量读**（1.5）：粗扫 ≤12 帧定区间 → 只在区间内密集抽；亚秒定位用 `-ss` 小数秒或帧号，一次抽一批候选点。**禁止逐帧线性扫**——这是历史上最大的耗时单点。
- **崩溃 / 闪退类 bug 先要崩溃日志再看录屏**（1.5.1）：跑 `scripts/parse_ips.py`，用日志时间戳反推录屏位置只抽 ±5s；多份 `.ips` 堆栈相同即可直接得出回归性结论。
- **拼图必须标设备并圈出问题部位**（1.7 B/C），用 `scripts/side_by_side.py`。
- **build 号 / link 目标 / 经办人偏好走 `bug-report-context.md` 记忆**（0.6），不要每次重问；用户给了新值立刻覆盖写回。
- **用户已给 link 目标 → 建完票必须 link**（4.4 / 4.8），这是建票流程的一部分，不是可选收尾。
- **token 按反引号精确提取**（4.2），memory 那行常带中文注释，**且标签大小写与冒号全/半角都不固定**（实测是「API Token：」）—— 用 `[Tt]oken[：:]` 容忍两种写法，取到空串要立刻报错，别当成 token 过期；跑查重前先 `myself` 自检一次认证，别把 401 当成「查重无命中」。
- 标题里的分隔符写字面 `>`，**不要 HTML 转义**（第 3 节）。
- **写进本文件的团队约定要带来源和日期**（如 `（团队约定，2026-08）`、`<JMA-xxxx> 实测, 2026-07-28`）——半年后才判断得出某条规则还算不算数、是谁定的。
- 项目专属约定（默认项目 key、经办人映射、语言要求、模块白名单、回归期硬追问）**属于项目级配置**，由各项目自己的 skill / CLAUDE.md 提供，本 skill 不硬编码。
